# 013 — Deletion drops all influence

The hard-delete cycle from the 2026-09-19/20 /plan session: a deleted field, card, or deck leaves no trace in the review or mastery ledgers, `mastery_log` gains an order that survives a scoped rebuild, one pair of functions plans and executes every deletion, and every delete confirm reports real counts. Branch: `feat/deletion-drops-influence`, after 012 landed. Archive (`field_def.archived_at`, its endpoints and read filters) stays in the code, dormant, per ADR 049 — nothing in this file touches it.

Reading order for a builder: ADR 047 is the rule every other decision here applies; read it first, then Contracts, then the task. Task 010's delta contract still reads "min id of attributed(c,f)"; per ADR 050 "id" there now means `reviewed_at`, and its wording is otherwise unchanged.

## ADRs

Decisions this file implements; full context and rejected alternatives live in the ADRs.

- **ADR 047 — Persistent entities never depend on ephemeral ones**: subject, deck, field, card, configuration, review log, and mastery log are persistent; practice run, practice deck, and practice card are ephemeral. Deleting an ephemeral entity touches nothing persistent except attribution, which nulls (a run delete keeps every review and mastery value, reaffirming ADR 039). Deleting a persistent entity deletes every record referencing its id, by foreign key or array, and recomputes every derived value; ephemeral dependents go only when they can no longer function. Updates affect nothing that references them, except that attribution is severed by a material edit. The three attribution pointers are the only persistent-to-ephemeral references. Supersedes ADR 015's owned-state-versus-history framing.
- **ADR 048 — Review history and snapshots cascade with their owner**: `review_log.card_id` and `field_def_id` become `NOT NULL ON DELETE CASCADE`, `practice_card_id` is dropped, `practice_deck.deck_id` becomes `NOT NULL ON DELETE CASCADE`, a run left with no decks is deleted, and the deleted-deck chip retires. No rebuild follows a card or deck delete. Supersedes the SET NULL half of ADR 015; amends ADR 011.
- **ADR 049 — Field deletion drops all influence**: the deck editor's remove-field is a hard delete; configurations naming the field and active runs naming it are deleted, its id is scrubbed from the deck's `shown_prompt_ids` arrays, its review rows cascade, and the deck's mastery is rebuilt, deck-scoped, to what the live path would have written without the field. Completed runs are untouched. Archive stays in the code, unexposed. Supersedes ADR 010's decision; amends ADR 011.
- **ADR 050 — `mastery_log` is ordered by `reviewed_at`, stamped under the card lock; its id is a uuid**: `record_review_group` assigns `reviewed_at` under the per-card advisory lock as the greater of the proposed stamp and the card's latest review timestamp plus one microsecond, so it is strictly increasing per card; `review_group_id` is stored as provenance only; `UNIQUE (card_id, field_def_id, reviewed_at)`. A rebuild of any scope reproduces every row's position. Amends ADR 042.
- **ADR 051 — One deletion closure plans and executes every deletion**: `compute_deletion_impact` returns the closure as ids by type, `apply_deletion` executes exactly it and is the only way a subject, deck, field, or card is deleted, and `GET /api/deletion-impact` returns the same closure as counts for the confirms. The delete transaction computes its own impact; the preview is advisory. A field whose deck is also being deleted contributes nothing on its own.

No other index. The unique constraint's backing index is what serves the latest-row `DISTINCT ON … ORDER BY reviewed_at DESC` queries; no separate index is added for them.

### The order (ADR 050)

The ledger's order is `reviewed_at`. Across the appearances of one card it is strictly increasing, because `record_review_group` assigns it under the card's lock (below); every row one appearance writes — one per rated answer field and one per shown prompt field — carries that appearance's single stamp, in `review_log` and `mastery_log` alike. So for one pair "latest row" means greatest `reviewed_at` and every `DISTINCT ON` and `ORDER BY` uses that one column (`ORDER BY reviewed_at DESC` for latest, ascending for a run's rows). No `order_key` helper exists. `review_group_id` on the row is provenance only. Rows of different cards may share a timestamp; nothing compares rows of different pairs by order, and the replay sorts groups by `(reviewed_at, review_group_id)` only to make its sequence deterministic across cards. A violation of the unique constraint is never caught: the `IntegrityError` propagates and the request fails, because it can only mean a write bypassed the lock discipline.

Stamping: `record_review_group(db, strategy, user_id, group, practice_run_id)` first takes `pg_advisory_xact_lock(hashtext(card_id))`, then replaces `group.reviewed_at` with `max(group.reviewed_at, db_read_latest_reviewed_at(db, group.card_id) + 1 µs)` (`dataclasses.replace`; a card with no reviews keeps the proposed stamp), then logs the group, then applies it. `submit_rating` keeps passing `datetime.now(UTC)` as the proposed stamp. The read and the write sit under one lock, and a second transaction for the same card blocks at the lock until the first commits, so its read sees the first's stamp; this relies on Postgres's default READ COMMITTED isolation, which the engine uses — never set an `isolation_level` on `create_engine`. The `max` also keeps a rating whose wall clock reads earlier than the card's latest review from landing before it. The lock order becomes card lock, then the group lock inside `db_log_review_group`, then `apply_rating`'s own lock line, which is the same transaction-scoped card lock re-entered; today's order is group then card. Neither order can deadlock, since every transaction takes the card lock before its group lock. A retry of an already-logged group recomputes a stamp, then `db_log_review_group` returns RETRY and nothing is written, so the persisted stamp is untouched. The rebuild never re-stamps: `_replay_review_groups` calls `apply_rating` directly with the persisted timestamps.

### The deletion closure (ADR 047, ADR 051)

`compute_deletion_impact(db, user_id, subject_ids=(), deck_ids=(), field_ids=(), card_ids=()) -> DeletionImpact` in `app/services/deletion.py`. A pure read. Steps, in order:

1. Ownership: for each type, the ids that are not owned by `user_id` (via the subject chain) or do not exist raise `LookupError("<subject|deck|field|card> <id> not found")` naming the first one.
2. `decks` = `deck_ids` ∪ decks of `subject_ids`.
3. `explicit_fields` = `field_ids` whose deck is not in `decks`. A field whose deck is being deleted is part of the deck cascade and contributes nothing on its own: no ADR 049 configuration lookup or run deletion (its pending cards cascade with the deck, so the run can still be rated), no affected cards, no scrub, no rebuild.
4. `fields` = `explicit_fields` ∪ active fields of `decks` (archived fields cascade too but are not counted; the user never sees them).
5. `cards` = `card_ids` ∪ cards of `decks`.
6. `configurations` = configurations of `decks` ∪ configurations whose four id arrays overlap `explicit_fields`.
7. `runs` = runs of `user_id` having at least one practice deck and whose every practice deck's `deck_id` is in `decks` ∪ active runs with a practice deck whose four id arrays overlap `explicit_fields`. Card ids contribute nothing here (ADR 048 deletes a run only when it has no decks).
8. `affected_card_count` = number of cards on the decks of `explicit_fields` that are not in `cards`; 0 when `explicit_fields` is empty.
9. `explicit_fields_by_deck` = `explicit_fields` grouped by their deck: the surviving decks and the fields each loses.

`DeletionImpact` (frozen dataclass): `subject_ids`, `deck_ids`, `field_ids`, `card_ids`, `configuration_ids`, `run_ids` as `frozenset[uuid.UUID]` (the closure, explicit ids included); `affected_card_count: int`; `explicit_fields_by_deck: Mapping[uuid.UUID, frozenset[uuid.UUID]]`.

### Executing the closure (ADR 051)

`apply_deletion(db, strategy: MasteryStrategy, impact: DeletionImpact) -> None` in `app/services/deletion.py`. In this order:

1. `db_delete_practice_runs(impact.run_ids)`
2. `db_delete_deck_practice_configs(impact.configuration_ids)`
3. `db_scrub_shown_prompt_ids(deck_id, field_ids)` for each entry of `explicit_fields_by_deck`
4. `db_delete_cards(impact.card_ids)`, `db_delete_field_defs(impact.field_ids)`, `db_delete_decks(impact.deck_ids)`, `db_delete_subjects(impact.subject_ids)` — bulk deletes by id; the FK cascades remove what the closure does not count (values, ledger rows, snapshots, practice cards, archived fields)
5. `db.flush()`. `apply_deletion` deletes with SQL statements; an object loaded before the call is not updated for rows the FK cascades remove, so a caller reads nothing it loaded earlier and reloads what it needs after
6. `rebuild_deck_mastery(db, strategy, deck_id)` for each key of `explicit_fields_by_deck`

No commit; no `touch`; no validation of the two-field floor (task 003 D3) (the batch edit and the dormant archive endpoint each enforce it for their own path). Callers:

- `delete_subject(db, strategy, subject)`, `delete_deck(db, strategy, deck)`, `delete_card(db, strategy, card)` in the same module: compute for the one id, apply, `touch` the parent (subject delete touches nothing; deck delete touches the subject; card delete touches the deck), commit.
- The batch edit (below) calls the pair inside its own transaction and commits at the end as today.
- The dormant `DELETE /fields/{id}` and `DELETE /fields/{id}/hard` endpoints are exempt per ADR 049 and unchanged. `DELETE /deck_practice_configs/{id}` is unchanged: a configuration's closure is itself, and its snapshots' `source_config_id` nulls by FK (ADR 040).

### Invariants a builder relies on

1. Every id in `review_log.shown_prompt_ids` is a live `field_def` id. Established once by the order migration's scrub, maintained by ADR 049's scrub and ADR 048's cascades. No runtime filter reproduces it; a violation fails loudly on `mastery_log.field_def_id`'s foreign key during replay.
2. `review_group_id` equals the id of the `practice_card` the appearance was rated against (`submit_rating` constructs it so). After ADR 048 it is the only link from a review to its appearance. A rebuild attributes a group to `practice_card.practice_run_id` when that practice card still exists and to `None` otherwise, which is what a live run delete leaves (ADR 047).
3. Replaying a deck's review groups in `reviewed_at` order reproduces the live rows for every group the deletion did not touch, value for value and timestamp for timestamp. `test_incremental_matches_rebuild` asserts this for the user-wide rebuild; T2 extends it to the deck-scoped one.
4. Every deletion of a subject, deck, field, or card goes through `compute_deletion_impact` then `apply_deletion`, inside the deleting transaction. No other code deletes those rows, and no delete path runs its own "what else goes" query.

### Migrations

**Order migration** (T1), `down_revision = "795ede6a41c4"`. Upgrade:

1. Tie check, before any other statement: `SELECT card_id, reviewed_at, count(DISTINCT review_group_id) FROM review_log GROUP BY card_id, reviewed_at HAVING count(DISTINCT review_group_id) > 1`. If it returns any row, the migration raises `RuntimeError` listing every row and changes nothing. Such a row means two appearances of one card were rated in the same microsecond; their application order decides which ledger state is latest and is recoverable only by reconstruction from the old `mastery_log`'s identity ids, which this file does not specify. The builder marks T1 `[BLOCKED]` with the rows as the replan brief. A downgrade cannot create a tie, since it only renumbers.
2. `UPDATE review_log SET shown_prompt_ids = ARRAY(SELECT x FROM unnest(shown_prompt_ids) AS x WHERE EXISTS (SELECT 1 FROM field_def WHERE field_def.id = x)) WHERE EXISTS (SELECT 1 FROM unnest(shown_prompt_ids) AS x WHERE NOT EXISTS (SELECT 1 FROM field_def WHERE field_def.id = x))` — establishes invariant 1 before the replay below, which would otherwise insert a `mastery_log` row for a field that no longer exists.
3. `DROP TABLE mastery_log`; create the new shape; import and call `rebuild_mastery(session, get_mastery_strategy())` exactly as `795ede6a41c4` does.

Downgrade: create the old shape, `INSERT INTO mastery_log_old (id, …) OVERRIDING SYSTEM VALUE SELECT row_number() OVER (ORDER BY reviewed_at, review_group_id), … FROM mastery_log`, swap tables. Plain SQL, no strategy math. Step 2 is not reversed; the docstring says so.

**Cascade migration** (T4), `down_revision` = the order migration. Upgrade, in this order:

1. `DELETE FROM review_log WHERE card_id IS NULL OR field_def_id IS NULL`
2. `DELETE FROM practice_deck WHERE deck_id IS NULL`
3. `DELETE FROM practice_run WHERE NOT EXISTS (SELECT 1 FROM practice_deck WHERE practice_deck.practice_run_id = practice_run.id)`
4. Drop `review_log.practice_card_id`.
5. `review_log.card_id`, `review_log.field_def_id`: `SET NOT NULL`; drop and recreate each FK with `ON DELETE CASCADE`.
6. `practice_deck.deck_id`: `SET NOT NULL`; drop and recreate the FK with `ON DELETE CASCADE`.

Downgrade reverses 4–6 (nullable, `SET NULL`, `practice_card_id` re-added nullable). Rows removed by 1–3 are not restored; the docstring says so.

### Frontend copy (MD-2, MD-3)

Clauses in this order: `removes {fields} from {cards_affected}` (or `removes {fields}` when `cards_affected` is 0), `deletes {cards_deleted}`, `deletes {n} deck configurations`, `ends {n} practices in progress`. This can't be undone.` A failed impact request renders through `setSaveError` and opens nothing.
