- Q44. How is Flashy hosted and deployed: the provider for the API and for the frontend, whether they share an origin, the managed PostgreSQL, Clerk's production keys, where `alembic upgrade` runs on a deploy, and where secrets live?
  - Reason: Deferred. Nothing in the repository deploys; `.github/workflows/ci.yml` runs tests and the migration chain only (ADR 041). Four things wait on the answer: mapping a database outage to 503 on every endpoint once the frontend and API are cross-origin (ADR 072); removing the local auth bypass in `app/dependencies.py` once local testing no longer needs it; rate limiting of `GET /api/health` (ADR 072); and a startup check that the database is at alembic head (ADR 045).
  - Owner: /code-decide
  - Rests on: nothing
- Q45. In what order does a practice show its cards, across its decks and within one, and where does a card come back after it is rated Again?
  - Reason: Deferred. A redesign of both is intended (ADR 058's Context) and nothing is decided for it. Today a practice shows its decks in the order the user ticked their configurations, each deck's cards unseen first then ascending mastery, and a retry returns after at least three other cards or at the end; the start order is written in no record, only in `start_practice_run`'s docstring in `app/services/practice_run.py`, while the retry's placement is ADR 037 and ADR 058.
  - Owner: /product-decide
  - Rests on: nothing
- Q46. Does the app show the user how their mastery has changed over time, for a card, a deck, a subject or a configuration, beyond the summary of one practice?
  - Reason: Deferred. Wanted later as a statistics surface. The app already keeps what it would draw on: every change of a card's mastery with the practice that caused it (ADR 042), and which configuration each practice ran (ADR 040, ADR 068). Today one practice's summary (PDR 010) is the only change the user sees.
  - Owner: /product-decide
  - Rests on: nothing
