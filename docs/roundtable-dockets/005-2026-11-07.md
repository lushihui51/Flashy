## Code decisions

- CD1. A `practice` table holds a kept practice: its user, its name and when it was made. `practice_run` is renamed `run`, and every `run` carries a not-null `practice_id`, `ON DELETE CASCADE`. The rename covers every name in which "practice" means one go through it: `practice_deck` becomes `run_configuration`, `practice_card` becomes `run_card`, every foreign key column follows its table, as `mastery_log.run_id`, the `session` names that mean a run become `run`, and models, `db_*` modules, services, routes, frontend modules and the generated types follow. Applied migrations keep their old names. The migration renames every constraint to ADR 054's convention, the `practice_session` names left by ADR 038 included.
  - Facts:
    - PDR 035 makes a practice a thing the user keeps and a run one go through it, and lets a practice exist before its first run.
    - Nothing sits above `practice_run`.
    - AGENTS.md carries a rename through every tracked file and literal.
    - The dev database still names `practice_run`'s constraints `pk_practice_session`, `ck_practice_session_status_valid` and `fk_practice_session_user_id_app_user`.
  - Rejected:
    - `practice_card` renamed `attempt`: it would name attempts not yet made.
    - `run_deck` for the run's copy: it names the row by its deck, not by what it holds.
    - ADR 038's names kept under a new `practice`: `practice_deck` would read as a practice's deck.
    - Runs grouped by a shared id with no `practice` table: a practice never run has nowhere to live.
  - Becomes true: every table name says whose it is, and a run reaches its practice through one foreign key.
- CD2. A `run` carries no `user_id`; every read and write of a run, a `run_configuration`, a `run_card` or a `run_counted_card` is scoped to its user through `practice.user_id` in the statement.
  - Facts:
    - ADR 034 keeps ownership in the query.
    - A run belongs to exactly one practice (CD1).
  - Rejected:
    - `run.user_id` kept beside `practice_id`: the two owners can disagree with nothing to catch it.
    - `run.user_id` kept with a composite foreign key to `practice (id, user_id)`: a constraint only to keep a copy in step.
  - Becomes true: a run's owner has one home.
- CD3. A `practice_configuration` table holds one row per deck of a practice: `practice_id` and `deck_id`, both `ON DELETE CASCADE`, the six array and count columns, and `UNIQUE (practice_id, deck_id)`. A practice's decks are its `practice_configuration` rows. Cutting a run copies each into a `run_configuration`. `deck_practice_config`, `run_configuration.source_config_id` and `run_configuration.source_config_name` are dropped.
  - Facts:
    - PDR 039 makes a configuration part of a practice, with no name, changed between runs and held within one.
    - A completed run's page shows how that run asked each deck (LPD12, LPD17), and a run of chosen cards carries `card_ids` (ADR 086), so the run's copy and the practice's configuration change at different times.
    - `source_config_id` is read by nothing that generates, validates or reruns, and `source_config_name` only names a configuration.
  - Rejected:
    - One `run_deck` table with a nullable `run_id` for the practice's configuration: every read must say which kind of row it wants, and one that forgets mixes them silently.
    - `deck_practice_config` kept with a `practice_id`: a table named for a deck, owned by a practice, with routes and an editor for a thing PDR 039 removes.
    - The latest run's copy as the practice's configuration: a practice never run has none, and an edit would change a frozen copy.
    - One JSON column on `practice`: no foreign key removes a deleted deck, and ADR 094's scrub works on uuid arrays.
  - Becomes true: a practice's decks and how each is asked live in one table, copied into a frozen `run_configuration` when each run is cut. This replaces ADR 040 and ADR 068, and ADR 096's configuration half.
- CD4. A partial unique index `uq_run_practice_id_active` on `run (practice_id) WHERE status = 'active'` holds one active run per practice. Starting a practice, in one transaction, reads its active run and applies ADR 073's completion to it when it has no pending card, returns it if still active, and otherwise creates one through `db_try_stage_create_run`, which returns `None` when the index refuses; on `None` it reads and returns the run a concurrent start created.
  - Facts:
    - PDR 038 allows one active run per practice and has starting the practice continue it.
    - ADR 073 completes a run only when its current card is read.
    - ADR 055 names a staged insert that reports a constraint failure by returning `None` `db_try_stage_<verb>_<noun>`.
  - Rejected:
    - A service check under a row lock alone: a path that forgets the lock makes two active runs silently.
    - A `practice.active_run_id` pointer: the same fact stored twice, kept in step by every path that ends or deletes a run.
    - The index alone, inserting first: every continue goes through a constraint failure, and a run with nothing left blocks new ones.
  - Becomes true: the database refuses a second active run, and starting a practice lands on the one run there is to go on with.
- CD5. Ending a run deletes every `pending` `run_card` of it and sets it `completed`, in one transaction, on a whole run and a run of chosen cards alike.
  - Facts:
    - PDR 038 completes an ended run as it stands, its summary speaking only of the cards it reached.
    - The summary, `run_progress` and the chosen-cards check read every `run_card` row of a run.
    - A pending row has no review.
  - Rejected:
    - Pending rows kept and filtered by every reader: a reader that forgets shows cards never reached.
    - An `ended` status: against ADR 073 and PDR 035's two states.
  - Becomes true: an ended run holds only rated attempts, a run ended before its first rating is a completed run with no cards, and no reader of a completed run knows it ended early.
- CD6. One service function cuts every run, for Start run with no active run, Re-run and Re-run these. It takes a practice and an optional list of cards, and for each `practice_configuration` validates it, cuts a `run_configuration` with `card_ids` null for a whole run or the deck's chosen cards, generates through `_snapshot_and_generate_deck`, and refuses with `no_cards` once, across every deck, when nothing was generated. Re-run and Re-run these never read the completed run's `run_configuration`; the completed run supplies only the chosen cards, each checked to be one of its cards. Re-run cuts with `card_ids` null.
  - Facts:
    - PDR 040 asks every next run by the practice's configurations as they stand, and Re-run over every card of the practice.
    - Today `start_practice_run`, `rerun_practice_run` and `start_chosen_cards_run` share `_snapshot_and_generate_deck` and the `no_cards` check.
  - Rejected:
    - ADR 076 and ADR 086 as they stand, copying the completed run's snapshots: a changed board would not reach the next run.
    - Three functions each reading `practice_configuration`: validation and refusal in three places.
  - Becomes true: every run is cut in one place, from the practice's configurations as they stand. This replaces ADR 076, ADR 085's three paths and its `nothing_to_rerun` and `nothing_to_practice` checks, and ADR 086's building of a run of chosen cards from snapshots and its rerun copying `card_ids`; ADR 086's nullable `card_ids` and a deleted card's id selecting nothing hold.
- CD7. A `run_counted_card (run_id, card_id)` table, primary key `pk_run_counted_card` on both, `run_id` and `card_id` each `ON DELETE CASCADE`, and an index `ix_run_counted_card_card_id`, holds one row for each card of the practice the run's configurations could ask, written when the run is cut by the same askability test generation uses, moved into one function. M is a run's count of those rows; N is its count of distinct `card_id` among its `run_card` rows that are not `pending`. Both are read for a list of runs in one grouped statement each.
  - Facts:
    - LPD22 fixes M at the run's start, leaves out a card that cannot be asked, and drops a deleted card from M and N.
    - CD5 deletes unreached rows, and a run of chosen cards generates only the chosen cards, so `run_card` cannot carry M.
    - `run_card.card_id` is `ON DELETE CASCADE`.
  - Rejected:
    - M counted over `run_card`: every ended run and run of chosen cards would read full.
    - A `run.counted_card_ids` array: a reader that takes its length counts deleted cards.
    - A `run.card_total` count: a deleted card leaves it too high, or the closure must decrement it and still misses ended runs and runs of chosen cards.
  - Becomes true: M and N stay right as cards are deleted, with no deletion code.
