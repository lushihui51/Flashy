The API serves no frontend files; in development the frontend's server forwards `/api` to the API, so the browser already sees one origin there. The code allows a second origin: the API's CORS setting takes a list of origins, and the frontend takes the API's address from a setting that defaults to its own origin. Every request carries an `Authorization` or `X-Timezone` header, which makes a browser ask permission first when the API is on another origin. A response the API fails to produce carries no CORS headers, so across origins the browser reports it as no connection, which is why a database outage would need mapping to 503 on every endpoint (ADR 072).
  - Rejected: The frontend on a static host and the API on an address of its own, because every request is preceded by a permission request, a failed response reads as a lost connection unless every endpoint maps its failures, and two things deploy that must agree on the API's shape. One origin through a static host that forwards `/api` to the API, because it is two providers, and the forwarding is a feature of the particular host.
  - Becomes true: One thing deploys, and the frontend and the API it was built against always ship together. The browser makes no cross-origin request in production, and the mapping of a database outage to 503 on every endpoint is no longer needed. A change to the frontend alone restarts the API. The frontend's files are served by the API's process with no content network in front; one can be added later with no change to the code. The deployed build needs Node and Python. Development runs as it does today, with two servers and nothing built.
- CD16. The service and its PostgreSQL run on Railway, in one project, on the Hobby plan. The database is Railway's PostgreSQL template as shipped, with no backups. The service's Serverless setting stays off, and the owner's domain is attached to the service.
  - Facts: CD15 deploys one service built from Node and Python. PDR 053 has a visitor see a filled app the moment the page opens. Under CD7 the example library exists only in the production database, and a script is run against production to make it. Railway's Hobby plan is $5 a month and includes $5 of usage, metered at $10 a GB of memory, $20 a vCPU and $0.15 a GB of volume a month, with volumes up to 5 GB and two custom domains a service, each given a certificate automatically. Railway puts a service to sleep only where its Serverless setting is turned on. Railway gives a volume its backups on the Pro plan and refuses them on Hobby. Railway maintains its PostgreSQL template as a single node while it is left as shipped. A pre-deploy command runs between build and deploy, and a failure stops the deploy. `railway ssh` runs a command inside the deployed service.
  - Rejected: Render, because a 512 MB service and its smallest paid PostgreSQL come to about $13 a month, above what the owner set out to spend, though its paid database can be restored to any moment of the past three days. Railway's Pro plan, because it is $20 a month, and the backups are all it adds at this size. A nightly job that dumps the database to storage elsewhere, because it is a part that can stop with nothing saying so, and the owner takes the risk of no backup until Q11 is answered. A Fly.io machine with Neon's PostgreSQL, because it is two providers, and the database either sleeps after five idle minutes with six hours of history, on the free plan, or costs about $19 a month kept awake. Fly.io's own managed PostgreSQL, because it starts at $38 a month. A rented server run by the owner, because the certificate, the updates, PostgreSQL and its backups all become the owner's to keep.
  - Becomes true: The app and its database are one bill, of about $5 to $8 a month at a handful of visitors. A database that is lost or damaged is gone, with the example library and every user's decks and practice, and a migration that destroys data cannot be undone. The database is one node with no standby, and while it restarts, the connection banner shows. The database's volume holds at most 5 GB on this plan.
- CD17. Production's settings live in the Railway service's variables and nowhere in the repository. `DATABASE_URL` is set as a reference to the PostgreSQL service's own variable, so the password is never copied by hand. `PERMITTED_ORIGINS`, `CLERK_FAPI_URL` and `VITE_CLERK_PUBLISHABLE_KEY` are set beside it. `test_database_url` becomes optional in `Settings` in `app/config.py`, and production sets none. `ENV` and `DEV_AUTH_USER_ID` are never set there. Development reads the two `.env` files as it does today, with its own database and Clerk's development instance, and no value of production's is in them.
  - Facts: `Settings` reads `database_url`, `test_database_url`, `permitted_origins`, `vite_clerk_publishable_key`, `clerk_fapi_url`, `dev_auth_user_id` and `env`, the first five required. The database's address holds its password and is the one secret among them. The API verifies a session against Clerk's public keys, fetched from `clerk_fapi_url`, and holds no Clerk secret. Clerk's publishable key is public by design and is built into the frontend's files. `test_database_url` is read only by `tests/conftest.py`. Both `.env` files are ignored by git. The bypass needs `ENV=development` and `DEV_AUTH_USER_ID` both set. The owner develops against a local server, a development database and Clerk's development instance, and keeps doing so.
  - Rejected: A `.env` file placed on the host, because it is a second copy of the password that someone keeps in step by hand. The database's address typed into the service's variables, because it goes stale when Railway changes the password or the host. `test_database_url` set in production to a made-up value, because the app would start with a setting that points nowhere and reads as real. A secrets manager apart from the host, because it is one more account for one secret.
  - Becomes true: The repository holds no production value. A new setting is added in Railway before the deploy that reads it, or the app fails to start. Whoever can open the Railway project can read the database's password. The frontend's build needs `VITE_CLERK_PUBLISHABLE_KEY` at build time, not only when the app runs. Development and production share no database, no Clerk instance and no setting's value.
- CD18. A deploy starts when a commit reaches `main`. Railway waits for CI on that commit, builds the service from a `Dockerfile` at the repository's root, runs `alembic upgrade head` as its pre-deploy command, and makes the new deployment live once `GET /api/health` answers 200. The `Dockerfile` builds the frontend in a Node stage, taking `VITE_CLERK_PUBLISHABLE_KEY` as a build argument, and copies the built files into the Python image that runs the API. Wait for CI, the pre-deploy command and the healthcheck path are set in the service's settings on Railway.
  - Facts: A change reaches `main` only by a pull request with CI green, and CI runs again on the push to `main` (ADR 041). `alembic upgrade` is the only way a schema changes, and the app creates no tables when it starts (ADR 045). `GET /api/health` pings the database (ADR 072). CD15 deploys one service built from Node and Python, and CD17 has the frontend's build need the publishable key. Railway deploys a linked repository when a commit is pushed to the connected branch, and with Wait for CI on, skips the deploy when a workflow fails. Railway builds from a `Dockerfile` at the root, and a variable reaches the build only where the `Dockerfile` declares it. A pre-deploy command runs between build and deploy in a container of its own, and its failure stops the deploy. With a healthcheck path set, the new deployment goes live only after the path answers, and the previous one stays live until then. Railway's settings files in the repository, `railway.toml` and `railway.json`, are deprecated, closed to new services, and stop working on 1 December 2026.
  - Rejected: The migration run when the app starts, because ADR 045 keeps schema changes out of startup, and a migration that fails would leave the app restarting in a loop. The migration run from CI, because CI would then hold the production database's password, against CD17. A workflow in GitHub that pushes the build to Railway, because it needs a Railway token kept in GitHub for what the linked repository does unasked. Railway's own builder working the project out, because the repository holds a Python app at its root and a Node app in a folder, and a `Dockerfile` states the build exactly and runs on another host unchanged. A deploy on every push without waiting for CI, because a merge that breaks `main` would go live. The three settings in `railway.toml`, because Railway is retiring it.
  - Becomes true: A merged pull request is live within minutes with no one acting, and nothing reaches production except through `main`. A migration or a health check that fails leaves the previous deployment serving. Between the migration and the switch, the previous deployment runs against the new schema, so a migration that removes something the old code reads fails its requests for that moment. Three settings live on Railway and in no file, where a change to them is seen by no review. The same `Dockerfile` would build the app on another host.
- CD19. Production has a Clerk production instance of its own, on the owner's domain, and the development instance stays for development. The production instance is made by cloning the development instance's settings, and its DNS records are added to the domain as Clerk's dashboard lists them. The service's variables hold its publishable key, its Frontend API address as `CLERK_FAPI_URL`, and the app's one address as the only entry of `PERMITTED_ORIGINS`.
  - Facts: Clerk requires a domain the developer owns for a production instance, serves that instance's Frontend API from a subdomain of it, and lists the DNS records to add in its dashboard; the records can take up to 48 hours to spread. A development instance is capped at 100 users, and Clerk calls it unsuitable for production. Clerk's dashboard offers to clone a development instance's settings into a new production instance, leaving out single sign-on connections, integrations and paths. User data cannot be moved between instances. A social sign-in runs on Clerk's shared credentials in development and needs the developer's own in production. Clerk's free plan allows 50,000 returning users a month for an app. The API accepts a session only when its issuer is `clerk_fapi_url` and its `azp` is in `permitted_origins`. The owner has a domain. CD17 keeps development and production apart in every setting.
  - Rejected: The development instance used for production, because it stops at 100 users, shows its sign-in on a development address, and Clerk says not to. A production instance started from Clerk's default settings, because the ways to sign in would then differ between development and production with nothing saying so.
  - Becomes true: No account made in development exists in production, the owner's included, so the account that makes the example library is made in production. Sign-in works in production only once the DNS records have spread, so they are added days before publishing. The app is reached at one address, and a session started at any other address of the service is refused by the API. Each social sign-in production offers needs credentials the owner sets up with that provider. Clerk costs nothing at the app's expected size.
- CD20. The app carries no rate limiter. A flood of requests is met on Railway: a hard usage limit of $20 a billing cycle caps the bill by taking the service offline, a usage alert below it warns the owner first, and Under Attack Mode is turned on by hand for as long as a flood lasts.
  - Facts: Under CD5 fourteen reads and the health route answer with no account, and each reaches the database. Under CD16 the bill follows what the service uses. The app is published for the people its owner gives its link to (PDR 053). Railway lets any plan set a hard usage limit, of $10 at least, and at the limit takes every workload offline until the limit is raised; it emails at 75, 90 and 100 percent of it, and at an alert amount the owner sets. Railway's edge stops attacks below the level of requests, and says its limits on floods of requests may not always be enough. Its Under Attack Mode, turned on per service for a set time or until turned off, puts a browser check before each new visitor and turns away anything that is not a browser. Railway watches a service's health only while it deploys.
  - Rejected: A limiter inside the app, counting by the caller's address, because every refused request still reaches the app's process, several people behind one address share one allowance, and its threshold would be chosen with no traffic to choose it from. A second provider's proxy in front of the domain, because it holds the domain's DNS, Clerk's records must go around it, and Railway says it cannot always issue a certificate behind one. Under Attack Mode left on, because every visitor would meet a browser check before the app, against PDR 053. A limit on the health route alone, because it is the cheapest of the fifteen routes open to anyone.
  - Becomes true: The API holds no rate-limiting code to keep. A flood can slow or stop the app for everyone until the owner acts or it ends, and nothing tells the owner but the usage emails. The worst month costs $20, and reaching that takes the app offline until the owner raises the limit, in a busy honest month as much as under a flood. When the app draws real traffic, this decision is the first to come back.
- CD21. The local bypass in `app/dependencies.py` stays as it is.
  - Facts: The bypass answers every request as one user only while `DEV_AUTH_USER_ID` and `ENV=development` are both set, and the app logs a warning at startup when it is on. A browser check runs under it, signed out of Clerk. CD9 adds a frontend switch that matches it. CD17 sets neither variable in production.
  - Rejected: Removing it, because a browser check would then need a real Clerk session inside a headless browser.
  - Becomes true: Local browser checks keep working as they do. A production service on which someone sets both variables answers every request as one user, and Railway's variables are the one place that could happen.
- CD22. The app makes no check at startup that the database is at alembic head.
  - Facts: Under CD18, `alembic upgrade head` runs before each deployment goes live, and its failure stops the deploy. A query that meets a schema it does not expect fails loudly (ADR 045). CI runs the whole migration chain from an empty database (ADR 041).
  - Rejected: A check that refuses to start when the database is not at the code's own head, because a previous deployment, restarted during a deploy or brought back to undo one, would find the database ahead of it and refuse to start.
  - Becomes true: A deployment never starts before its own migrations have run. A database changed by hand, outside alembic, is found only by the query that meets the difference. A previous deployment brought back starts against the newer schema, and works or fails by what that schema changed.
