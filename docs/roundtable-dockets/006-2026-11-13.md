## Lesser decisions

- LPD1 The page that says what Flashy is is reached by "About" at the side menu's foot, set apart below the main places, and headed "About Flashy". It holds, in order, Flashy's one-line description; its three ideas, each a heading over one line; and "How it works" over four numbered steps, from deck and card to practice, run and summary. It draws no block and nothing yellow, and a thin line parts the ideas from the steps. Its words are VC1's and VC2's.
  - Facts: Nobody reads long paragraphs. Nothing on the page can be tapped, and the page has no main action. In Flashy's own menu, "About" can mean only Flashy.
  - Rejected: A strip at the foot of every page, because it collides with a form's bar and crowds the run page. Long paragraphs of explanation, because few finish them. A second line under the heading, because it is too wordy. The logo's yellow F in the heading, yellow discs behind the ideas' icons, a wavy yellow underline under each idea's heading and a yellow marker stroke through each, because the plain page is preferred and every one but the F gives yellow a meaning beside the main action. "About Flashy" in the menu, because "About" says it beside "Privacy". "About" as the heading, because someone arriving straight at the page reads nothing saying what it is about.
  - Becomes true: The user reads what Flashy is and how to use it on one phone screen, one tap on the menu away.
  - Drawings: 8
- LPD2 Deleting an account is "Delete account", below "Log out" in the account sheet. It opens a confirm headed "Delete your account?" over "Your decks, cards, practices and runs will be gone, with your mastery. This can't be undone.", with "Cancel" and "Delete".
  - Facts: Every deletion in Flashy confirms with the thing's name and "This can't be undone."
  - Rejected: Typing "DELETE" to confirm, because no other deletion asks it and it slows a user who has decided. "Delete your account? This can't be undone." alone, because the user is not told their mastery goes.
  - Becomes true: A user reads exactly what they lose before deleting their account.
  - Drawings: 10
- LPD3 The privacy page is reached by "Privacy" in the side menu, directly below "About", and headed "Privacy". Under its heading it reads VC8's opening line, then six headings, each over its words, as VC8 gives them. The address to write to is underlined inside its sentence and opens the person's email app.
  - Facts: Google's review asks a privacy policy to say what is collected, who receives it, how it is deleted and whom to contact.
  - Rejected: The address as a block, because a block for one address at the foot of a page of text is out of place. The address as plain text, because the user copies it by hand.
  - Becomes true: A person reads, in under a minute, what Flashy keeps about them, and writes to Flashy's owner in one tap.
  - Drawings: 9, 11
- LCD1 Deleting an account is `DELETE /api/account`, `delete_account` in a new `app/routers/api/account.py` behind `CurrentUserDep`, answering 204, through a service `delete_account` in a new `app/services/account.py` that owns the transaction; the Clerk call is a function in a module of its own. When Clerk answers anything but success, or cannot be reached in time, the route answers 502 with a detail carrying the code `clerk_unavailable`, which has no sentence of its own, so the confirm shows "Flashy is having trouble right now. Try again in a moment."
  - Facts: `failureSentence` renders a 5xx carrying no known code as "Flashy is having trouble right now. Try again in a moment." 503 carries `database_unavailable` (ADR 130). A confirm shows its failure inside itself. With `DEV_AUTH_USER_ID` set, `CurrentUserDep` answers as that Clerk id. Clerk's docs do not say what its server API answers for an unknown id.
  - Rejected: `DELETE /api/me`, because `me` matches no name in the code or the vocabulary. A sentence of its own for `clerk_unavailable`, because the existing sentence is true of it. 503, because `database_unavailable` already answers with it.
  - Becomes true: The next developer tests the route without Clerk by replacing one function. A developer who deletes their account on the dev servers with the local bypass on deletes that id's user in Clerk's development instance.
- LCD2 The account sheet's delete confirm runs one TanStack Query mutation of `DELETE /api/account`. On success it calls `clerk.signOut()` and nothing else, so `useViewer()` turns to `guest` and ADR 132's one function loads Home afresh in the example library. On failure the confirm stays open with `failureSentence`'s sentence inside it.
  - Facts: ADR 132 loads Home afresh when `useViewer()`'s answer changes between `guest` and `user`, and nothing else reacts to a log-out. Clerk's docs do not say whether deleting a user ends the session its browser client holds.
  - Rejected: Loading Home without `signOut()`, because ADR 132 lets nothing else react to a log-out, and a session Clerk's browser client still holds would create an empty `app_user` again. Waiting for Clerk's browser client to notice the deletion, because no doc says it does, or when.
  - Becomes true: The user whose account is deleted lands where logging out leaves them. A request already in flight when the 204 arrives still creates an empty `app_user`, and nothing between the 204 and `signOut()` starts another.
- LCD3 "Delete account" has no guard for the example user while it holds a Clerk identity. The docstring of `attach` in `app/scripts/example_user.py` says that "Delete account" on the attached account deletes the example library.
  - Facts: `attach` gives the example user's row a Clerk identity so its library can be edited through the app, and nothing in the row then tells it apart from another user's. Only the owner runs the script. A guest holds no Clerk session, never sees the account sheet, and gets 401 from every route of a method other than `GET`.
  - Rejected: A column marking the example user, with a refusal, because it needs a migration, a code and a sentence, and an example user made without the script would leave it unset. A configured Clerk id the service refuses, because it fails silently once another account is attached.
  - Becomes true: A press of "Delete account" between an `attach` and the next `detach` deletes the example library, which is then made again by hand.
- LCD4 The page that says what Flashy is and the privacy page are the routes `/about` and `/privacy` inside the error-boundary route of `frontend/src/App.tsx`, rendering `AboutPage` and `PrivacyPage` in `frontend/src/pages/`, each writing its words in JSX, with no query and no `Breadcrumb`. `FOOT_NAV_ITEMS` in `frontend/src/components/shell/navItems.ts` holds "About" then "Privacy", and `SideDrawer` renders it at its foot, below `NAV_ITEMS`, with the same `NavLink` blocks.
  - Facts: ADR 128 answers an address outside `/api` that names no file with the frontend's `index.html`. Google's sign-in review opens the home page and the privacy page in a browser that runs JavaScript; this is inferred and unconfirmed.
  - Rejected: The words in a Markdown file rendered at runtime, because it adds a dependency and a renderer for the underlined link, and parts the words from a layout LPD1 and LPD3 fix. One `TextPage` fed an array of lines, because About's numbered steps and Privacy's link give the array a type for each kind of line.
  - Becomes true: A guest and a user reach both pages with no change to the server. If Google's review needs the policy readable without JavaScript, the privacy page does not serve it.
- LCD5 Every link inside a sentence is `InlineLink` in `frontend/src/components/ui/`: an `<a>` underlined in its text's color, with no block classes and no length of its own, taking `href` and its children. A router `Link` joins it when the first link inside a sentence to a page of the app does.
  - Facts: No link inside a sentence exists, and every link and button carries the block classes. The privacy page's address is the first link inside a sentence.
  - Rejected: A plain underlined `<a>` in `PrivacyPage`, because the next link inside a sentence would likely take the block classes. A utility class beside `tappable`, because a class cannot keep the underline to a link.
  - Becomes true: The next developer finds PDR 063's link inside a sentence in one component.
- LCD6 `Breadcrumb` draws only its places, widest first, and imports neither `hasEarlierPage` nor `ChevronLeft`; its tests assert it draws no "Back" button.
  - Facts: `Breadcrumb` draws the "<" on a deck's page, a practice's page and the run page through `hasEarlierPage()`.
  - Rejected: A "<" whenever `idx` is above 0, because PDR 064 gives no page but a form a way back of its own.
  - Becomes true: No page shows a "<".
- LCD7 README.md holds only what changes with a record: Flashy's one-line description and its three ideas; how a user goes from a deck to a practice, a run and its summary, naming no screen's controls; the lasting choices of how it is built, its stack, its layers, its review and mastery ledgers and its deletion closure, with no tunable value; how to run it locally, with every variable `Settings` requires; how it is deployed; and its license. It holds no section on what is or is not built.
  - Facts: README.md describes a summary with badges for first try, one retry, several retries and failed; says how a practice asks a deck has no screen, Home and search are placeholders and Flashy is not deployed; and says nothing of the example library. Its status, its screens' details and its tunable numbers are the parts that no longer match the app. The page that says what Flashy is tells its user what Flashy is and how to use it.
  - Rejected: README.md as it stands, rewritten to match the app, because its status and its screens' details drift again with the next cycle. The one-line description and the set-up alone, because its reader would learn nothing of Flashy's ideas or how it is built.
  - Becomes true: The next developer changes README.md only in a change that carries a record touching what it states, a variable of `Settings` included.
