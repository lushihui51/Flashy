# ADR 050: mastery_log is ordered by reviewed_at, stamped under the card lock; its id is a uuid

## Status

Accepted. Amends ADR 042: the ledger's order is `reviewed_at`, not the identity id, and the id is a uuid with no ordering meaning. ADR 042's rejection of CASCADE on the run foreign key stands.

## Context

ADR 042 made the BIGINT identity id the ledger's total order and called `reviewed_at` display data. That holds while every insert is a live append, because ids then follow time. ADR 049 needs a deck-scoped rebuild, which deletes one deck's rows and re-inserts them, giving them ids above rows other decks wrote later in time. Order inside the deck still follows time; order across decks no longer does. One reader depended on the cross-deck order: the breakdown's "before" lookup for a field the run never touched bounds by the run's first row across all its decks (task 010's delta contract), so after a scoped rebuild an untouched field's pre-run row could sit above the bound and read as never reviewed. The id was carrying two jobs, identity and order, and the second cannot survive a partial re-insert.

The intrinsic order is the review's timestamp, but as stamped it was not a total order per card: `submit_rating` sets `reviewed_at = datetime.now(UTC)` before any lock, and the per-card advisory lock that serializes the ledger write is taken later in `apply_rating`. Two appearances of one card — the same deck open in two runs — could carry equal timestamps yet be applied in a definite order. The rebuild already sorted by `(reviewed_at, review_group_id)` while the live path ordered by insert: two definitions of order that could disagree under a tie, with `review_group_id` a random uuid that says nothing about sequence.

## Decision

- `mastery_log.id` is a uuid supplied by the application on every insert. It identifies a row and orders nothing.
- The ledger's order is `reviewed_at`. `record_review_group` takes the per-card advisory lock first, then assigns `reviewed_at` as the greater of the proposed stamp and the card's latest review timestamp plus one microsecond (`db_read_latest_reviewed_at`, served by `ix_review_log_card_id_reviewed_at`), then logs the group, then applies it. Within a card the stamp is therefore strictly increasing in application order, and a tie within a `(card, field)` pair cannot exist. "Latest row per pair" is greatest `reviewed_at`; every `DISTINCT ON` and `ORDER BY` uses that one column, and the breakdown's bounds are timestamps.
- `review_group_id` is stored on every row as provenance. It is never an order key. `UNIQUE (card_id, field_def_id, reviewed_at)` replaces the id-ordered index.
- Rows of different cards may share a timestamp. Nothing compares rows of different pairs by order; the replay sorts groups by `(reviewed_at, review_group_id)` only to make its sequence deterministic across cards.
- A rebuild never re-stamps: it replays the persisted timestamps, so a rebuild of any scope gives every row the position it had.

## Alternatives considered

### Keep identity order and bound untouched pairs by the run's first row for the same card

Rejected. It fixes the one reader that was found, not the category: any future reader that compares ids across pairs would break silently after a scoped rebuild.

### A separate sequence column

Rejected. A counter assigned at insert cannot be regenerated by a rebuild; the rebuilt rows would land at the end again.

### `(reviewed_at, review_group_id)` as a composite order, uuid as tie-break

Rejected. The uuid is random. Under a tie it can order two appearances opposite to how they were applied, so "current mastery" would return the row that misses the second review's effect, and a rebuild would write different values than the live path did.

### Stamp with Postgres `now()`

Rejected. It is transaction start time, shared by every row in a transaction and by concurrent transactions; it makes ties more likely, not less.

## Consequences

Benefits:

- Order is intrinsic to the review a row came from, so scoped and user-wide rebuilds reproduce every row's position, and the breakdown's bound contract keeps its wording.
- The before-bound query compares one column instead of a row value.
- The unique constraint gives `record_review_group`'s idempotency a database backstop it did not have.

Costs:

- A stamp may be nudged a few microseconds past wall clock when a card is rated twice within one microsecond; invisible in any display.
- The migration replays the whole ledger once, and must fail loudly if any card already has two groups on one timestamp.
- Every latest-row query orders by a timestamp rather than an integer; still an index range scan.
